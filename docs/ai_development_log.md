## 3. Approximate AI-generated code share

**Close to 100% of the lines; considerably less than 100% of the decisions.**

Essentially every line in `src/`, `scripts/` and `tests/` was written by Claude. Stating that as "~95% AI-generated" would be accurate about authorship and misleading about the process, because the human contribution was not typing — it was direction and acceptance:

- **Sequencing.** The human chose which phase ran when, and overrode the AI's proposed order more than once — pulling the rule engine forward from phase 7 into phase 2 because its output feeds the feature matrix, and running the survival model first because it was the highest-risk component.
- **Scope.** Each phase was authorised individually. The AI proposed; it did not decide what got built.
- **Acceptance.** Every phase ended with measured results reviewed before the next began.

The honest summary: the AI was a fast implementer and a diligent measurer, and the human was the architect and the reviewer.

## 4. Representative prompts

Prompts were short and directive. The useful pattern was to name a phase and let the model report what it found, rather than specifying implementation:

```
"i want to win this challenge so what more can i do"
"phase 8"
"submission then"
"start"
```

The prompt that produced the most value was the first: asking for a gap analysis against the actual rubric before writing any code. That surfaced the 15-point time-to-event category, which the original architecture had omitted entirely.

The LLM layer's own prompts — the ones sent at runtime — are in `src/llm/prompts.py`, and every runtime call is logged verbatim to `logs/llm_calls.jsonl`.

### What only a live model could find

The rows above were caught by measuring the pipeline. A second class of defect was invisible until a real LLM was pointed at the guardrails — nine of them in about half an hour, none findable by inspection or by the fault-injection tests, which all passed throughout:

| Defect | Why fault injection missed it |
|---|---|
| A retired model name returning HTTP 404 on every call | The catalogue changed between writing the code and running it |
| Free-tier rate limiting, with escalating SDK backoff | No limit exists on a local template provider |
| Unicode hyphens in dates breaking numeric grounding — **51 of 58 rejections** | We do not write en-dashes in test fixtures; the model does |
| A date component grounding a fabricated statistic | Introduced *by* the previous fix, and it made the guardrail silently **accept** invented numbers |
| `next-3-month` parsed as minus three | Only appears when a model hyphenates a phrase we had only ever underscored |
| Negative scenario deltas having no percentage form | Nothing generated a negative probability until the model described a decline |
| `print()` crashing on non-ASCII model output | Templates are pure ASCII; a Windows console is cp1252 |
| Empty completions counted as guardrail rejections | The template provider never returns nothing |
| Correct derived arithmetic rejected as ungrounded | We never thought to test a model doing its own subtraction |
| A narrow no-break space as a thousands separator (`13 104.95`) split into two numbers | We write `13104.95`; the model writes it the European way |

**The guardrail was wrong far more often than the model was.** Nine of these ten were defects in our own validator, against one genuine, reproducible model failure. Every one was invisible to fault injection for the same reason: we do not write en-dashes, hyphenated phrases or European thousands separators in test fixtures, and a model does.

After the fixes, the final clean run on `openai/gpt-oss-120b` accepted 13 of 14 live generations with zero ungrounded numbers, while all six fault-injection classes were still caught -- so the false positives were removed without blunting the check.

The fourth row is the one that matters. Rows three and five were **loud** — they rejected valid output, which is visible and annoying. Row four was **silent**: it widened the number pool until a reporting date could ground a fabricated portfolio average, which is precisely the failure the component exists to prevent. Every fault-injection test still passed while it was broken.

**Fault injection proves a guardrail catches what you thought of. Only real adversarial input proves what you did not.** Six invented failure classes all passed; one live model with typographic punctuation and a habit of doing arithmetic found three real defects in the same component.

Two of the AI's own tests were also wrong, and the code was right: one rejected the substring "causes" in phrasing whose required disclaimer is "not established causes", and one had an off-by-one threshold bound. Both were corrected in the test, not the code.

## 6. Human review process

1. **Phase authorisation.** Nothing was built without an explicit instruction naming the phase.
2. **Measured reporting.** Each phase ended with computed numbers, including the ones that were disappointing — prepayment unpredictability, engineered features adding nothing to default, a persistence baseline beating a trained model.
3. **Regression tests on every defect.** 156 tests exist, and the ones that matter encode specific past failures rather than coverage for its own sake.
4. **Generated documentation.** The model card and this log are generated from artifacts, so they cannot drift from the numbers they describe.

## 7. Lessons learned

**Every real defect in this project was found by a number that looked too good.** Not one was found by reading code. A 1.000 AUC meant a broken rule; a 1.2% precision meant an off-by-one in a groupby; a submission that passed every schema check had half its portfolio sharing one probability. The productive instinct was disbelief at good news, and it would have been just as valuable without any AI involved.

**AI is fastest at exactly the work that hides errors.** It produces plausible, well-structured, confidently-commented code at a rate no human matches, and plausible-and-wrong is the hardest failure to spot. The counterweight is not more review of the code — it is running it and interrogating the output.

**A component that validates other systems needs adversarial input, not just unit tests.** The output guardrail had six fault-injection cases, all passing, and was wrong in three different ways the first time a real model was pointed at it — including one direction where it silently accepted fabricated numbers. Testing it against text we wrote ourselves tested our imagination, not the guardrail.

**Guardrails belong on outputs, not in instructions.** The LLM prompts say "do not invent numbers". That makes fabrication unlikely. The validator in `src/llm/grounding.py` makes it non-shippable. The same lesson applied to the AI writing this codebase: the instruction to avoid leakage mattered far less than the test that truncates a fixture's future and asserts the past did not move.

**A prompt instruction is not a control, and two models proved it.** The reviewer prompt explicitly requires a sentence marking the output as a recommendation rather than a decision. Both `gpt-oss-20b` and `gpt-oss-120b` omit it -- it was the dominant genuine rejection on each, independently. One model doing that is an anecdote; two is evidence that the instruction does not enforce the policy and the output check does.

**The most valuable prompt was a question, not an instruction.** Asking what would score well against the actual rubric, before writing code, found a missing 15-point category. Asking for implementation first would have produced a polished system with a hole in it.
